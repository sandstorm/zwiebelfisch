# Concept: an embeddable Typst editor for non-technical users

_2026-10-10. Based on [2026_10_10_prior-art-research.md](2026_10_10_prior-art-research.md)._

## 1. The idea in one picture

People who use Word or OnlyOffice today should be able to write Typst documents. Typst should stay
what it is: plain text in git, any Typst feature allowed, and clean diffs.

```
┌──────────────────────────── <typst-editor> widget ────────────────────────────┐
│ [ Visual | Source ]   B  I  H1 H2  • 1.  ⎘                                      │
├───────────────────────────────────────┬────────────────────────────────────────┤
│  LEFT: editing view (pick one)        │  RIGHT: live preview                   │
│                                       │                                        │
│  Visual  = Word-like (ProseMirror)    │   ┌──────────────┐                     │
│            Hello *world* is shown as  │   │ Hello world  │  ◄── click here     │
│            "Hello **world**"          │   │ • first      │                     │
│                                       │   │ • second     │                     │
│  Source  = plain Typst (CodeMirror)   │   └──────────────┘                     │
│            = Hello *world*            │         │                              │
│            - first                    │         │ jumps to the source          │
│            - second           ◄───────┼─────────┘ and highlights it            │
└───────────────────────────────────────┴────────────────────────────────────────┘
```

- **Two ways to edit the same text.** The *Visual* view looks like Word: bold is bold, a list is a
  list, and Enter makes a new bullet. The *Source* view is the raw Typst. Switching between them
  loses nothing.
- **Preview on the right.** It is the real compiled Typst output, so it matches the PDF exactly.
  Clicking anything in it jumps to the matching place in whichever editing view is active.
- **Anything the Visual view does not understand** (`#set`, `#show`, custom functions, and so on) shows up
  there as a small grey "Typst code" box. You can still edit it inline, and it is never lost or
  rewritten.
- **The editor is a JS widget** (`<typst-editor>` / `createTypstEditor(el, …)`) that any web app can
  embed. Later, a server adds real-time co-editing and loads and saves files in GitLab.

## 2. The central rule: the Typst text is the only truth

Everything you see is computed from one string of Typst text. None of the views keeps its own
document that could drift away from it.

```
                         ┌───────────────────────┐
                         │      Typst text       │   the only source of truth
                         │  "= Hello *world*\n…" │   (later: a shared Y.Text)
                         └───────────┬───────────┘
                                     │ parse (Lezer, incremental, keeps every byte)
                                     ▼
                         ┌───────────────────────┐
                         │      syntax tree      │
                         └──┬────────┬────────┬──┘
              derived view  │        │        │  derived view
                 ┌──────────┘        │        └───────────┐
                 ▼                   ▼                    ▼
        ┌────────────────┐  ┌────────────────┐  ┌──────────────────┐
        │  Source view   │  │  Visual view   │  │     Preview      │
        │  (CodeMirror)  │  │ (ProseMirror)  │  │ (compiled pages) │
        └───────┬────────┘  └───────┬────────┘  └────────┬─────────┘
                │ edits             │ edits              │ clicks
                └──────── become text edits ─────────────┘
                          back on the Typst text
```

Why do it this way rather than the usual WYSIWYG approach (keep a rich document, export Typst)?

- Other people can keep using a plain text editor or git on the same file.
- Collaboration only has to merge **text**, which is a solved problem (Yjs).
- Unknown or new Typst features can never break the editor or get lost.

## 3. How a Visual edit stays minimal

The difficult part is turning a Word-like edit back into Typst **without rewriting the whole file**.
Most markdown WYSIWYG editors re-print everything, so `_x_` turns into `*x*`, and line breaks and
comments move. We take a different approach: each block in the Visual view remembers which
characters of the text it came from.

```
 Typst text                                     Visual view (ProseMirror)
 ───────────────────────────────────            ─────────────────────────────
 0   #set page(margin: 2cm)   ───────────────►  [ Typst code: #set page(...) ]   raw box
 24                                             
 25  = Report                 ───────────────►  Heading 1: "Report"
 34                                            
 35  Sales were _good_.       ───────────────►  Paragraph: "Sales were good."
     ▲                                                          ▲
     │                                                          │ user types " very"
     │   only this slice is re-printed:                         │ before "good"
     │   "Sales were _good_."  →  "Sales were very _good_."     │
     │                                                          │
     └──── smallest text edit: insert "very " at offset 46 ◄────┘
           (everything else stays byte-for-byte identical)
```

1. **Text → Visual:** walk the syntax tree. Headings, paragraphs, bold, italic, lists and links
   become real ProseMirror nodes. Everything else becomes a raw box holding its original text.
   Every node records its `[from, to]` range in the text.
2. **Visual → text:** after an edit, re-print **only the block that changed**. Unchanged children
   reuse their original text slice. Compare the old slice with the new one and apply the smallest
   insert or delete to the text.
3. **Text → Visual again** (when someone types in the Source view, or a colleague edits
   remotely): re-parse, then replace only the affected blocks in the Visual view.

## 4. How click → source works

Hit-testing is the reason we need **our own small compiler module**, written in Rust and compiled
to WebAssembly. Only the Typst compiler knows which glyph on a page came from which character of
the source. The official `typst-ide` crate exposes exactly this as `jump_from_click` and
`jump_from_cursor`.

```
  Preview (browser)                   typst-engine (Rust → wasm, Web Worker)
  ─────────────────                   ──────────────────────────────────────
  user clicks page 2 at (120, 340)px
  convert to points ────────────────► jump_from_click(page 2, x=90pt, y=255pt)
                                        • walk the laid-out frames of page 2
                                        • find the glyph under the point
                                        • glyph → span → source offset
  highlight text[512..530]  ◄──────── { from: 512, to: 530 }
  in Source / Visual view

  cursor moves in editor
  offset 512 ───────────────────────► jump_from_cursor(512)
  scroll preview, flash  ◄──────────── [{ page 2, x 90pt, y 255pt }]
```

### Which renderer? Decision: our own `typst-engine` crate

| Option | Click → source | Effort | Verdict |
|---|---|---|---|
| **typst.ts** (`@myriaddreamin/*`) | ❌ the span plumbing in the npm builds is unused, and there is no `jump_from_click` | low to start, then a dead end that needs a patched Rust build anyway | no |
| **Own crate: `typst` + `typst-svg` + `typst-ide` → wasm** | ✅ `jump_from_click` / `jump_from_cursor` built in | one Rust crate of about 300 lines | **yes** |
| **Server-side compile** (tinymist preview or a Rust service) | ✅ | the same Rust code plus a server to run | later, optional |

The own crate is a single **deep module**. Its interface is small:

```
TypstEngine
  setFile(path, text | bytes)        // sources, images, fonts
  compile()        → { pages: [{ svg, width, height, hash }], diagnostics }
  jumpFromClick(page, x, y) → { path, from, to } | null
  jumpFromCursor(path, offset) → [{ page, x, y }]
```

Behind that interface it hides: the Typst `World` (files, fonts, packages), incremental
recompilation (Typst's comemo caching), SVG export, and hit-testing.

- **Official output.** It uses `typst-svg`, the same renderer the Typst CLI uses. There is one Typst
  version and no third-party fork.
- **Per-page SVG with a content hash.** The preview swaps only the pages that changed, which is
  enough for documents of tens of pages. typst.ts's incremental vector format is something we can
  add later if very large documents need it.
- **The same crate can run natively on a server later** (for server-side PDF export or a
  thin-client mode). So "browser or server" is a deployment choice, not a rewrite.

## 5. The modules (A Philosophy of Software Design: deep modules, hidden details)

```
┌──────────────────────────────── TypstEditor (widget) ────────────────────────────────┐
│ createTypstEditor(el, { files, main, provider? })  →  { destroy, … }                │
│                                                                                       │
│   ┌────────────────────┐        ┌────────────────────┐        ┌────────────────────┐  │
│   │    SourceView      │        │    VisualView      │        │      Preview       │  │
│   │ mount, reveal      │        │ mount, reveal      │        │ update, onJump,    │  │
│   │                    │        │                    │        │ reveal             │  │
│   │ hides: CodeMirror, │        │ hides: ProseMirror,│        │ hides: worker,     │  │
│   │ Typst highlighting │        │ projection,        │        │ wasm engine, page  │  │
│   │                    │        │ minimal write-back,│        │ swapping, pt↔px    │  │
│   │                    │        │ raw boxes          │        │                    │  │
│   └─────────┬──────────┘        └─────────┬──────────┘        └─────────┬──────────┘  │
│             └──────────────┬──────────────┘                             │             │
│                            ▼                                            │             │
│              ┌──────────────────────────┐        text (debounced)       │             │
│              │      TypstDocument       │ ──────────────────────────────┘             │
│              │ text, tree, change(),    │                                             │
│              │ onChange()               │                                             │
│              │ hides: storage (string → │                                             │
│              │ Y.Text), parsing, echo   │                                             │
│              │ suppression              │                                             │
│              └──────────────────────────┘                                             │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

Each library is known to exactly one module: only `SourceView` knows CodeMirror, only `VisualView`
knows ProseMirror, only `Preview` knows the worker and wasm, and only `TypstDocument` knows how text
is stored.

## 6. Later: collaboration and GitLab

```
  Browser A                         Server                                GitLab
  ─────────                         ──────                                ──────
  TypstDocument ◄─┐
   (Y.Text)       │ Yjs updates   ┌──────────────────────┐   load files    ┌─────────┐
                  ├──────────────►│ Hocuspocus (Node)    │◄────────────────│  repo   │
  Browser B       │  (WebSocket)  │ • auth hook          │                 │         │
  TypstDocument ◄─┘               │ • persist Yjs state  │  commit on      │         │
   (Y.Text)                       │   (Postgres / S3)    │  "Save version" │         │
                                  │ • GitLab sync        │────────────────►│         │
                                  └──────────────────────┘                 └─────────┘
```

- **Only the text is shared**, as one `Y.Text` per file. CodeMirror binds through
  `y-codemirror.next`. The Visual view is still computed locally from that text. This is how every
  Typst collaboration project works today (TeXlyre, TOSS, collabst). What we add is the Visual view
  on top.
- **Server: Hocuspocus** (the standard Yjs server). It handles auth, debounced storage and scaling.
- **GitLab:** load the repository tree and files through the API on first open. "Save version"
  creates one commit (`POST /projects/:id/repository/commits`, with `last_commit_id` so concurrent
  changes are detected). If GitLab moved in between, merge and apply the result as text edits. An
  alternative is one branch per session plus a merge request, which fits "Publish".
- **Images and fonts** are stored by reference (path plus SHA), not inside Yjs.

## 7. What exists already, and the gap

Every open-source Typst web editor (TeXlyre, TOSS, collabst, TypstDrive) is the same stack:
CodeMirror, typst.ts and Yjs. None of them has a Word-like view that keeps the text as the truth.
- The Typst WYSIWYG prototypes (ortic/typst-wysiwyg, TyX) store their own model and *export* Typst.
- Markdown WYSIWYG editors (Milkdown, Quarto, Tiptap) re-print the whole file.
- Overleaf's LaTeX Visual Editor follows the right rule (text is the truth), but it only decorates
  the code editor.

**A Visual view that maps back to the source, over Typst, is the new part.** Details are in the
research doc.

## 8. Milestones

1. **Engine + preview:** the `typst-engine` wasm crate compiles to per-page SVG. The widget shows the
   preview.
2. **Click → source:** `jump_from_click`, which highlights in the Source view. Then cursor → preview.
3. **Source view:** CodeMirror with Typst highlighting and a live preview while typing (worker,
   debounce).
4. **Visual view v1:** paragraphs, headings, bold/italic, lists and raw boxes, with minimal
   write-back. Round-trip tests.
5. **Visual view v2:** toolbar, editing raw boxes inline, links, images, tables.
6. **Workspace:** multiple files, images, Typst packages, self-hosted fonts.
7. **Collaboration:** `Y.Text`, a Hocuspocus server, GitLab load and commit.

## 9. Engineering rules

- Tools and versions come from mise only, with exact pins. Every script is a mise task in
  `mise-tasks/`.
- Tests come first. vitest covers the engine, projection and round-trip logic (it runs anywhere).
  Playwright covers user-visible behaviour.
- Code follows APOSD (deep modules, information hiding). Quality is tracked with complexity
  metrics: `mise run quality`, `mise run quality:report`, and the `code-quality` skill.
